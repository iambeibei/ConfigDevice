## 老化架设置界面三项改造（调研结论，待实施）

- **持久化现状**：老化架已持久化到 `AppContext.BaseDirectory\AgingShelves.json`（exe 同目录），链路是
  `AttachAutoSave → AutoSaveHandler → SaveAgingShelves`（任何 PropertyChanged 立即全量覆写）。
  「重启应用」「Tab 切换」都能保留；真正的丢失点是 **TextBox 默认 UpdateSourceTrigger=LostFocus**
  （`EditableReadValue` 样式没设），窗口关闭时正在编辑的字段不会回写到 VM，也就不会落盘。
  修复方向：绑定改 `UpdateSourceTrigger=PropertyChanged` + autosave 加防抖（否则每敲一个字符写一次文件）。
- **发现的真实缺口**：第一页的 `ReadSERVER_IP` / `ReadSERVER_UDP_Port` / `ReadIsRoot` / `ReadUDPPort`
  等基础配置**完全没有持久化**，重启后全丢；老化架字段倒是有的，两者不对称。
- **串口刷新现状**：`SerialModel.GetPortNames()` = `SerialPort.GetPortNames()`；`MainViewModel.RefreshAvailablePorts()`
  仅在 SelectedComPort 不在新列表且新列表非空时才回退选择 → **列表为空时 SelectedComPort 不会被清空**（小 bug）。
  自动刷新要在 `View/MainWindow.xaml.cs` 挂 `HwndSource.AddHook` 处理 `WM_DEVICECHANGE`(0x0219) 的
  `DBT_DEVICEARRIVAL`(0x8000) / `DBT_DEVICEREMOVECOMPLETE`(0x8004)，并用 DispatcherTimer 防抖。
- DataContext 由 XAML `<vm:MainViewModel />` 声明、`App.xaml` 的 `StartupUri` 指向 MainWindow，关窗即退应用，
  所以「退出后重新进入」和「完全重启应用」在当前结构下是同一回事。

## 三项改造调研（同一天追加，产出 `docs/LightGateway-改造计划.md`）

需求：(1)「读取」与「写入并重新读取」合并为单一按钮并在读完后自动绑定老化架；(2) 基本信息持久化核实；
(3) 串口列表改为 USB 插拔事件驱动刷新。只出计划，未改业务代码。

调研新增的关键事实（补充到上面的结论）：
- **持久化真缺口**：只有老化架模板进了 `AppContext.BaseDirectory\AgingShelves.json`；基础配置 `Read*` 全族、
  `ExternaldeviceList`、串口选择/波特率、上次选中的老化架与点位，**全部是 MainViewModel 的纯内存属性**。
  `App.xaml.cs` 无 OnExit、MainWindow 无 Closing 钩子 → 退出不保存。
- **现网隐患**：`AutoSaveHandler` 每次 PropertyChanged 都全量 `File.WriteAllText`，写到一半异常 → 坏 JSON →
  下次 Load 反序列化失败 → 弹窗并把 `AgingShelves` 重置为空 → 再存一次就真丢数据。必须改去抖 + 原子写。
- **`SerialModel.CloseSerial()` 有真 bug**：`Close()` 后又 `Dispose()` 且不重建 `_serial`，之后再 `OpenSerial`
  会在已释放对象上设属性/打开，必抛异常。这是「串口自动刷新」的前置必修项（拔→自动关→插回→再开 是标准路径）。
- **流程合并的坑**：`SelectReadShelfItem()` 会把下拉框强制切成 `ReadAgingShelfItem`（`RemoteId` 为空），
  所以「自动绑定」所需的老化架 id **必须在回显之前**先算好，否则取到的 `SelectedAgingShelf` 一定判空。
  另外 `TryResolveAssignIds` 缺 id 时会弹阻断弹窗，合并后要改成软失败降级为「仅读取」。
- **`写入并重新读取` 名不副实**：它不写设备，只调服务端 AssignDevice 写绑定关系；`写入`(ChangeConfig) 才是写设备，
  两者不能混淆。自动化后属于「静默写服务端」，必须保留用户确认或明确的不再提示开关。
- **串口自动刷新方案**：`MainWindow.xaml.cs` 挂 `HwndSource.AddHook` 处理 `WM_DEVICECHANGE`(0x0219) 的
  ARRIVAL(0x8000)/REMOVECOMPLETE(0x8004)（项目已有 WindowActivationHelper 的先例），忽略 DEVNODES_CHANGED(0x0007)
  避免消息风暴；DispatcherTimer 去抖 300-500ms，插入后再延迟 ~1s 做一次校验刷新（驱动装完前枚举不到 COM）。
  列表变化时才重新赋值 `PortNameList`，否则 ItemsSource 重绑会重置 ComboBox 选中。

## 需求一口径修订（用户澄清 + 逐行核对，同一次会话）

- 用户明确：**只合并两个写入按钮**（`写入` + `写入并重新读取`），不动 `读取` / `读取并匹配老化架`；
  绑定 API 放在**写入之后、自动回读校验成功之后**再调。
- **重大发现：`case "写入"`(line 181) 其实已经在做这件事** —— 写 ChangeConfig → 遮罩 → RunReadBackDelayAsync
  → `DoReadConfig()` → `TryMatchAgingShelfFromRead()` → `CheckWriteOK` → 一致则 `await AssignDeviceAndRereadAsync()`。
  所以 `写入并重新读取`(line 287) 剩下的唯一价值是"手动补绑/重试"，可以直接删掉。
- **真正的 bug（自动绑定基本走不通）**：`TryMatchAgingShelfFromRead()`(line 604) 会把 `SelectedAgingShelf` 改写成
  本地匹配模板或 `ReadAgingShelfItem` 伪项（RemoteId 为空 → `GetSelectedRemoteRackId()` 返回 null）；
  且 SelectedAgingShelf 变化会重拉点位 → `LoadAvailablePointsAsync` 里 `SelectedAgingPoint = null!`。
  于是紧接着被调用的 `AssignDeviceAndRereadAsync()` 里 `TryResolveAssignIds` 必失败，弹
  "请先选择…老化架/点位"，可用户明明选过了。修复 = **写入前先把 RemoteId/点位 id/节点 ID/IsRoot 快照下来**，
  API 参数只从快照取；`TryResolveAssignIds` 增加接受快照的重载。
- 其他约定：`TryResolveAssignIds` 在自动流程里失败要降级为状态文本而非 MessageBox；
  `写入` 成功后不再重复 `DoReadConfig()+SelectReadShelfItem()`（冗余且二次切下拉框）；
  绑定失败 ≠ 写入失败，文案必须区分。
- 计划文档已改写为 `docs/LightGateway-改造计划.md` 第三章（现状/目标链路/改动点/要点/风险），实施顺序里需求一提到最前（步骤 0）。
